### SHOULD-FIX

- **SHOULD-1 — Emoji used as the app-wide icon language.** Header (`☀ ☾ ☰ ⋔ 🤖 📊 ⚙`), toolbar
  (`↶ ↓ ⇣ ↑ ▾ ↺ ⟳`), sidebar glyphs (`● ⎇ ☁ ⊟ ⌥ ◎ ›`), file-row actions (`🕑 👁 🗑 ↺ ✨ ⋯`), and

  in `menuIcons.tsx`). Verdict + migration plan in **§C**. Large, incremental follow-up; not a

- **SHOULD-2 — Onboarding last step exposes three dismiss controls.** `OnboardingOverlay.tsx`
  renders top-right `✕` (`:214-222`, `onClose`), a footer left button relabeled Skip→**Close** on
  the last step (`:239-241`, `onClose`), and the primary **Finish** (`:251-253`, `goNext`→
  `onClose`). The footer "Close" duplicates "Finish". **Fix = §B.1** (drop the Skip button on the
  last step; keep `✕` + Finish, the standard dialog pairing).

- **SHOULD-3 — `--accent` as text colour over `--selection` fails AA (latent, TODO A9).**
  Confirmed by measurement: `--accent` on `--selection` = **3.51:1 dark** (`#4f8cff` on `#2a3b57`)
  / **3.74:1 light** (`#2f6fe4` on `#dbe7ff`) — both below the 4.5:1 body-text floor. `--text-1`
  on `--selection` = **9.36:1 dark**, so the fix is free. **Audit result:** no *same-rule*
  instance pairs `background: var(--selection)` with `color: var(--accent)` today (the five
  selection fills — `context-menu.css:58`, `search.css:279`, `settings-primitives.css:345`,
  `settings-shell.css:107/276` — all use `--text-1`/`--text-2` text or `border-color: --accent`),

  selection-filled ancestor (`status-panel.css:207` is the prime suspect). **Rule to enforce
  (§B.2):** selected/active row *text* is always `--text-1`; accent may carry the state only via a
  left border, dot, or ring (edge contrast needs 3:1, which `--accent` meets).

- **SHOULD-4 — HEAD branch name is marginal on hover.** `sidebar.css:136-143` paints the checked-out
  branch name/glyph in `--accent`. On the base sidebar surface this is fine (**5.07:1** on `--bg-1`),
  but `.branch-row:hover { background: var(--bg-2) }` drops it to **4.48:1** — 0.02 under AA, and it
  is 13px/600 which does **not** qualify as large text. Nudge: use `--text-1` for the name text and
  keep `--accent` only on the glyph/`aria-current` treatment (see §D), or darken the hover wash. Low
  urgency (0.02), but it compounds with SHOULD-3 as the same anti-pattern.

## B. Redesign specs

### B.1 Onboarding footer (fixes SHOULD-2)

Target: `src/components/OnboardingOverlay.tsx` footer block (`:238-254`). Behaviour, not layout,
changes — reuse the existing `.onboarding-footer`, `.onboarding-skip`, `.btn-secondary`,
`.btn-primary` classes and current geometry.

Rules:
- **Left slot (Skip):** render **only when `!isLast`**. Label always `Skip`; never relabel to
  `Close`. `onClick={onClose}`.
- **Right group:** `Back` (render when `idx > 0`) + primary. Primary label = `Get started`
  (welcome) / `Next` (middle) / `Finish` (last), as today.
- **Top-right `✕`:** unchanged on every step; it is the universal overlay dismiss.

Resulting footer per step:

```
welcome:   [ Skip ] ......................... [ Get started ]      (+ ✕)
middle:    [ Skip ] ................ [ Back ] [ Next ]             (+ ✕)
last:      [      ] ................ [ Back ] [ Finish ]           (+ ✕)
```

Last step now has two dismiss paths — `✕` (leave immediately) and `Finish` (complete) — which is
the conventional dialog pairing, not the current three. Empty left slot on the last step is
correct (footer actions are right-aligned via `space-between`). No token, motion, or a11y change;
initial focus and Esc handling stay as they are.

### B.2 Selection / active-row text contrast rule (fixes SHOULD-3, SHOULD-4)

Canonical rule (parks into ui-reference §2/§11 once MUST-1 is resolved):

> **Never use `--accent` (or any hue) as the text colour of a selected or hovered row.** Selected/
> active row text is `--text-1`; muted metadata stays `--text-2`. State is carried by the
> `--selection` fill plus, optionally, a 2px `--accent` left border / dot / ring — non-text
> surfaces where `--accent` need only clear 3:1 (it does: 5.07:1 on `--bg-1`, 3.5:1 on
> `--selection`, both ≥3 for graphics).

Concrete edits:
- `sidebar.css:136-138` — change `.branch-row-head .branch-name` to `color: var(--text-1)` (keep
  `font-weight: 600`). Keep `.branch-row-head .branch-glyph { color: var(--accent) }` (glyph is a
  graphic, 3:1 suffices) and add `aria-current="true"` on the HEAD row (see §D) so the checked-out
  branch is conveyed by weight + glyph + AT, not hue alone.
- Verify `status-panel.css:207` (the A9 suspect): if `color: var(--accent)` sits on a row that can
  take `background: var(--selection)`, switch the text to `--text-1` and, if an accent cue is
  wanted, add a `2px solid var(--accent)` left border on the selected state.
- No new token. `--text-1` on `--selection` = 9.36:1 dark / (light `#1c1f24` on `#dbe7ff` ≈ 13:1),
  both pass comfortably.

## C. Icon-system verdict

**Verdict: the emoji/Unicode glyphs are NOT acceptable; standardise on the existing inline-SVG
set.** This is a house-consistency and cross-platform-rendering defect, not a matter of taste. The
project already defines the correct idiom in `src/components/menuIcons.tsx` (P10 §4.2): 16×16,
`viewBox="0 0 16 16"`, `stroke="currentColor"`, `stroke-width:1.4`, round caps/joins, no fill —
explicitly "matches the graph glyphs in draw.ts". Emoji break every property that idiom
guarantees: colour-emoji (`🤖 📊 🕑 👁 🗑 🕸️`) inject multi-colour raster glyphs into a monochrome
dark UI and cannot inherit `currentColor` for hover/disabled/focus; dingbats (`☀ ☰ ⋔ ⇣ ⌥ ◎ ⊟`)
drift in weight/baseline/coverage across Windows/macOS/Linux fonts. `ui-reference.md` takes no
explicit stance today (it is truncated — MUST-1), but the shipped `menuIcons.tsx` contract *is*
the de-facto standard; emoji are the deviation.

**Scope: large, do it incrementally, not as one blocking change.** Priority by how badly the glyph
misrenders:

| Tier | Glyphs | Why first | Existing SVG? |
|---|---|---|---|
| **P1 colour-emoji** | `🤖`(AI assets) `📊`(health) `🕑`(file history) `👁`(blame) `🗑`(delete) `✨`(AI) `🕸️`(onboarding) | multi-colour raster in a monochrome UI; worst OS variance | `🕑`→`HistoryIcon`, `🗑`→`DeleteIcon`, `✨`→`SummarizeIcon` already exist; `👁`,`🤖`,`📊` **new** |
| **P2 dingbat chrome** | header `☀ ☾ ☰ ⋔ ⚙`; toolbar `↶ ↓ ⇣ ↑ ▾ ↺ ⟳`; sidebar `● ⎇ ☁ ⊟ ⌥ ◎`; `⋯` overflow | inconsistent weight/baseline/coverage | `↺`→`ResetIcon`/`RevertIcon` exist; rest **new** |
| **P3 plain text glyphs** | `+ − × ›` , ahead/behind `↑N ↓N` | render acceptably as text; lowest priority, convert opportunistically | `›`→CSS `.file-chevron` (keep) |

**Approach:**
1. Add one new chrome-icon module `src/components/appIcons.tsx` (NOT appended to `menuIcons.tsx`,
   which is already ~280 lines) reusing the exact `svgProps` recipe. New glyphs needed:
   `SunIcon`/`MoonIcon`, `ListIcon`/`TreeToggleIcon`, `RobotIcon`, `ChartIcon`, `GearIcon`,
   `UndoIcon`, `FetchIcon`, `PullIcon`, `PushIcon`, `CaretDownIcon`, `RefreshIcon`, `CloudIcon`,
   `StashIcon`, `WorktreeIcon`, `DetachedIcon`, `RefDotIcon`/`RefBranchIcon`, `EyeIcon`, `MoreIcon`.
2. Migrate one surface per increment: (a) file-row actions (mostly reuses existing icons +
   `EyeIcon`, cheapest win), (b) `HeaderToolbar`, (c) `WorkspaceToolbar` (pair with MUST-3 aria
   fix), (d) sidebar glyphs (pair with §D), (e) onboarding illustrations.
3. Icon buttons keep their existing `.btn-icon`/`.row-action`/`.branch-glyph` boxes and colour
   tokens; only the glyph child changes emoji → `<Icon/>`. SVG sizes: 14px in `.btn-icon`/`.sidebar`
   (match `.sidebar-add-icon svg { 14px }`), 16px in menus/file rows.
4. The brand `🌱` (window/onboarding) should become a dedicated logo SVG for crispness, but it is
   low priority (appears rarely, is intentional brand).

**Deferral note:** this is a multi-increment epic; ship P1 first (visible, cheap, mostly-existing
icons), then P2. Do not block the sidebar-keyboard work (§D) on it.

## D. Sidebar keyboard-accessibility contract (blocking deliverable)

Makes every sidebar row operable by keyboard, consistent with the graph's Up/Down/PageUp/PageDown/
Home/End nav and the app's ARIA conventions. **senior-dev implements; this section is the spec.**

### D.1 Model choice — `role="tree"` with roving tabindex

The sidebar is a sectioned, collapsible navigation whose Branches/Remotes/Tags sections already
render a nested directory `<Tree>` (`Tree.tsx` emits `role="tree"/treeitem/group` + `aria-expanded`).
Collapsible groups + nested dirs = genuinely hierarchical, so **`role="tree"`** is the honest ARIA
(and the VS Code Source-Control model the target user knows). `role="listbox"` is rejected: it
cannot express expand/collapse or the nested branch dirs.

**One composite tree, one Tab stop, roving tabindex.** The whole sidebar nav is a single
`role="tree"`; exactly one item has `tabIndex=0` (the "active" item), all others `tabIndex=-1`.
Tab enters the tree at the active item and Tab/Shift+Tab leave it; arrows navigate within. This
mirrors the graph canvas (one focusable widget, arrows move inside).

**Section action buttons and filter inputs are left as their existing separate tab stops** (the
"+"/cleanup buttons, the per-section `ListFilterInput`). They are NOT tree items. This preserves
current keyboard access to them with zero regression; arrow-navigation of the tree simply skips
them. (Alternative considered — folding row/section actions into the treeitem reachable by a
secondary key — is more work and hijacks Tab inside the tree; not recommended for v1. Flagged for
the orchestrator: accept the interleaved Tab order, or invest in in-item action nav later.)

### D.2 Roles, levels, attributes

| Element | Role | Attributes |
|---|---|---|
| sidebar nav wrapper (new, around the six sections) | `tree` | `aria-label="Repository sidebar"` |
| section header button (`SectionHeader.tsx`) | `treeitem` | `aria-expanded`, `aria-level="1"`, roving `tabIndex` |
| flat row `<li>` (branch/remote/stash/submodule/worktree/tag) | `treeitem` | `aria-level="2"`, roving `tabIndex`; HEAD branch adds `aria-current="true"` |
| `<ul class="branch-list">` | `group` | — |
| Tree dir `<li>` (`Tree.tsx`) | `treeitem` (already) | `aria-expanded` (already), add `aria-level` = depth+1, roving `tabIndex` |
| Tree leaf row (BranchRow/RemoteRow inside Tree) | `treeitem` | `aria-level` = depth+2, roving `tabIndex` |
| Tree root `<ul>` when embedded in the sidebar tree | `group` (NOT `tree`) | add a `Tree` prop `asGroup?: boolean` — no nested `role="tree"` |
| detached-HEAD info `<li>` (`Sidebar.tsx:547`) | `treeitem` | `aria-level="2"`, `aria-disabled="true"` (readable, no actions) |
| skeleton rows | unchanged | stay `aria-hidden` |

Every treeitem also carries a `data-tree-item` attribute (order/lookup) and a stable `key` string,
namespaced to avoid collisions: `header:<section>`, `branch:<name>`, `remote:<name>`,
`stash:<index>`, `submodule:<name>`, `worktree:<name>`, `tag:<name>`, `dir:<fullPrefix>`,
`detached`.

### D.3 Keys

Movement (handled centrally on the tree root — see D.4):

| Key | Action |
|---|---|
| ArrowDown | focus next visible treeitem (across sections) |
| ArrowUp | focus previous visible treeitem |
| Home | focus first treeitem |
| End | focus last visible treeitem |
| PageDown / PageUp | move by one viewport page = `floor(scrollViewport.clientHeight / 24)` items (min 1) — parity with the graph's page nav |
| printable char | type-ahead: focus next visible treeitem whose accessible name starts with the char (SHOULD; may land as a fast-follow) |

Structure + activation (resolved against the focused item's descriptor):

| Key | On a group (section header / tree dir) | On a leaf row |
|---|---|---|
| ArrowRight | collapsed → expand; expanded → focus first child | no-op |
| ArrowLeft | expanded → collapse; collapsed → focus parent (top-level header: no-op) | focus parent group header |
| Enter / Space | toggle collapse | **primary action** (D.5) |
| ContextMenu key / Shift+F10 | (optional) open section overflow if one exists, else no-op | **open the row's action menu** (D.6) |

Esc while a row is focused and no menu is open: do nothing (let App's global Esc run). Space must
`preventDefault` to avoid scrolling the pane.

### D.4 Focus controller (new files — I spec, senior-dev builds)

- `src/components/sidebar/SidebarTreeContext.ts` — context providing `{ activeKey, setActiveKey }`.
- `src/components/sidebar/useSidebarTreeNav.ts` (~150 lines) — owns `activeKey` state and returns:
  - `rootProps`: `{ role:'tree', 'aria-label':'Repository sidebar', ref, onKeyDown }`.
  - the `onKeyDown` implements D.3 movement by querying visible items in DOM order at event time:
    `Array.from(root.querySelectorAll('[data-tree-item]')).filter(el => el.offsetParent !== null)`
    (collapsed groups aren't rendered, so they never appear), locating `document.activeElement`,
    and moving/focus-ing the target. Movement calls `.focus()`; each item's `onFocus`
    → `setActiveKey`, keeping roving state and DOM in sync. O(n) per keypress is fine (sidebars are
    hundreds of rows at most, fewer when collapsed).
  - default `activeKey` = the HEAD branch row if present, else the first section header.
- Each treeitem reads `activeKey` from context and sets `tabIndex={key===activeKey?0:-1}`, spreads
  `role`/`aria-level`/`data-tree-item`, wires `onFocus={()=>setActiveKey(key)}`, and owns its OWN
  `onKeyDown` for the activation/structure keys in its column of D.3 (Enter/Space/Arrows-Left-Right/
  ContextMenu). Movement keys it does not handle bubble to the root controller. Expand/collapse is
  delegated to the toggle the item already owns (`SectionHeader` `onToggle`; `Tree` internal
  `toggle`), so no duplicate collapse state.

This split (central movement, per-item activation) is the standard roving-tabindex pattern and
keeps each row's action/menu callbacks where the data already is.

### D.5 Primary action (Enter/Space) per row type

| Row | Primary action |
|---|---|
| Local branch, not HEAD | **Checkout** (same as double-click; guarded by `!busy`) |
| Local branch, HEAD | no-op (already checked out); menu still available via ContextMenu key |
| Remote-tracking / configured remote / stash / submodule / worktree / tag | **open the row's action menu** (these rows have no single safe default; opening their menu *is* their activation) |
| Detached-HEAD info row | no-op |

Uniform rule to document: *Enter/Space = the row's primary action; branches check out, and any row
whose only affordance is its context menu opens that menu.* This keeps Enter meaningful everywhere
while ContextMenu/Shift+F10 remains the explicit "menu" gesture (identical to Enter for menu-only
rows, distinct for branches). Flagged as a deliberate decision, not a gap.

### D.6 Context-menu invocation + focus restore (reuses `ContextMenu.tsx`)

- Open on ContextMenu key / Shift+F10 (and Enter for menu-only rows) using the **row's rect**, not a
  cursor: `const r = rowEl.getBoundingClientRect(); open({ x: r.left + 8, y: r.bottom })`. Pass the
  same `items` the existing `onContextMenu(...)` right-click path builds. `ContextMenu` already
  clamps to the viewport (`ContextMenu.tsx:340`) and `autoFocus`es its first item.
- **Focus restore (hard requirement):** the Sidebar container must remember the triggering row's
  key/ref before opening and, on `ContextMenu` `onClose` (Esc, click-away, or item activation),
  return focus to that row (`setActiveKey(key)` + `ref.focus()`). Right-click never needed this, so
  it is new container responsibility — do not rely on `ContextMenu` for it. The menu itself already
  traps focus, handles arrows/Esc, and has `role="menu"`.

### D.7 Focus-visible treatment

- Use the global ring verbatim: `2px solid var(--accent)`, `outline-offset: 1px`, `:focus-visible`
  only (`tokens-and-base.css:156`). Rows have `border-radius:4px`, which the outline follows.
- **Clip check:** the ring extends 3px beyond the row box. `.branch-list` has `padding:0` and rows
  have `padding:0 4px`, so verify the `.sidebar` content region has ≥4px inner horizontal padding
  (in `layout-panes.css`); if the row sits flush to the pane's left edge, add 4px inner padding so
  the ring is not clipped. Do **not** switch to an inset/negative-offset ring (inconsistent with
  the rest of the app).
- No hover background is added on focus; the ring alone marks the focused/active row. `aria-current`
  + weight (not colour) marks the HEAD row (§B.2). Density-independent (rows are 24px in both
  densities — NIT-1).

### D.8 Tree.tsx changes (tree-mode participation)

`Tree.tsx` is generic (also renders status files), so change it additively:
- New prop `asGroup?: boolean` → root `<ul>` uses `role="group"` instead of `role="tree"` when
  embedded in the sidebar tree (no nested trees).
- Dir `<li>` gains `aria-level` and roving `tabIndex`/`onFocus`/`onKeyDown` (ArrowRight/Left/Enter →
  its existing `toggle`); it consumes `SidebarTreeContext`.
- Leaf slot: the caller's `renderLeaf` `<li>` (BranchRow/RemoteRow) already becomes a `treeitem` via
  D.2; Tree just needs to pass the correct `aria-level` down (add an optional `level` arg to
  `renderLeaf`, or wrap the slot). Keep Tree's file-tree callers (status panel) unchanged by gating
  the roving/context wiring behind `asGroup`.

**Delivery tiering (implementation note, not a spec compromise):** the model above is complete.
Ship it in two passes to keep diffs reviewable — **Pass 1:** the controller + flat rows + section
headers (covers flat-list mode, the default, and every section header). **Pass 2:** `Tree.tsx`
tree-mode participation (D.8). Both passes land the same `role="tree"` semantics; Pass 1 alone
already makes flat mode fully operable.

### D.9 Harness states to verify (all keyboard behaviour is harness-verifiable except SR announce)

Fixtures (`src/ipc/mock/`) needed — most already exist; confirm coverage:
- many local branches (flat AND tree mode), remote branches, tags (flat + tree), ≥3 stashes,
  ≥2 submodules, ≥2 worktrees;
- detached-HEAD case; empty sections ("No branches yet" / "No stashes" / "No remotes");
- pathological long branch name + deep tree path (focus ring must not break the ellipsis).

Verify in-harness (AI gate): Tab enters the tree at the HEAD row; Up/Down/Home/End/PageUp/Down move
focus with a visible ring on every row type; Enter checks out a non-HEAD branch; Enter/ContextMenu
key opens the menu at the row and Esc restores focus to that row; Left/Right collapse/expand section
headers and tree dirs. **USER CHECKPOINT:** actual screen-reader announcement (NVDA/VoiceOver reading
role/level/expanded/current). No motion is introduced, so no frame-timing checkpoint.

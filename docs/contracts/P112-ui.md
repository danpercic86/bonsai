## 0. What this contract needs from the architect — read first

> **SUPERSEDED IN WHOLE 2026-09-15 (§16.1). Historical.** All four items were answered by
> sub-increments 1–3 and are **shipped**. AMEND-1 and AMEND-3 landed as asked; **AMEND-2 landed in a

The architect's file as of 2026-09-11 still states §8.2 / OQ2: *"there is deliberately no 'browse to
an executable' button"*. The orchestrator's brief supersedes that (user ruling, same day). The
amendments below are what the Browse button and the not-installed marker require. **Each is a data
shape I cannot design around; none is a preference.**

**AMEND-1 (blocking the not-installed state) — the scan must be able to name an undetected id.**
`ExternalToolScan` carries only *detected* tools, so a kept-but-stale selection (`editorTool:
'zed'`, zed absent) leaves the frontend holding an opaque id and no label. Rendering `zed` raw is
not house quality and `notepadpp` is not a word. Add to `ExternalToolScan`:

```rust
/// Display labels for EVERY catalog entry of this kind, ANY os — the picker still
/// OFFERS only `terminals` / `editors`. This exists solely so a selection that is
/// not currently detected can be named. Static `&'static str` data, no IO.
pub terminal_labels: BTreeMap<String, String>,   // id -> label
pub editor_labels: BTreeMap<String, String>,
```
All-OS coverage is required because `coerce_tool_id` deliberately keeps any-OS ids (§5.2 of the
architect's contract: settings.json may be synced between machines).
*Fallback if refused:* render the raw id in `var(--font-mono)` and the note as
`The editor you chose isn’t installed right now.` — a measurably worse state; take AMEND-1.

**AMEND-2 (blocking Browse) — `'custom'` as a pseudo-id plus a backend-write-only path.**
A browsed absolute path is not a catalog id, and `coerce_tool_id` maps anything unknown to `""`, so
the renderer cannot store it. Do **not** encode it as `terminalTool: "custom:C:\..."`: that value is
destroyed the moment the user picks anything else, and any renderer echo of the stored settings
(a full-state resend, a failed-patch requeue) coerces it to `""` — a silent loss. Instead:

| Wire key | Rust field | Written by | Meaning |
|---|---|---|---|
| `terminalTool` / `editorTool` | `terminal_tool` / `editor_tool` | renderer (coerced) | adds one legal value: `"custom"` |
| `customTerminalPath` / `customEditorPath` | `custom_terminal_path` / `custom_editor_path` | **`pick_external_tool` only** | absolute path the native dialog produced; **never** assigned from a patch |

`coerce_tool_id` accepts `"custom"` as a catalog-adjacent id and is otherwise unchanged. The two
path fields are absent from `UiSettingsPatch` entirely, so `set_ui_settings` has no way to reach
them — that is the whole security property, and it makes switching away from and back to `custom`
lossless. `picked("custom", kind)` rechecks the stored path (`is_file` + exec bit, or `is_bundle`)
and returns `None` when it is gone ⇒ auto ladder, identical to the stale-catalog-id case.

**AMEND-3 (blocking Browse) — the command.**
```rust
/// P112: open the NATIVE program picker and, on confirm, write `custom_*_path`
/// and `*_tool = "custom"` itself. The renderer cannot supply a path — it only
/// asks for the dialog. `Ok(None)` = the user cancelled: nothing is written.
#[tauri::command]
pub async fn pick_external_tool(kind: ToolKind) -> Result<Option<DetectedTool>, AppError>
```
Returns the resulting entry with `id: "custom"`, `source: "custom"` (new `ToolSource` variant),
`label` = the display name (macOS: bundle name minus `.app`; else the file stem — `Code`,
`sublime_text`, `nvim`), `detail` = the absolute path. Rejection is a single category error; the UI
never shows its text (§8, `BROWSE_ERR`).
**Sub-case to resolve, not for me:** when `*_tool == "custom"` but the stored path is gone, the UI
needs the path and the label to render the missing-custom state. Simplest: `list_external_tools`
always returns the custom entry when `custom_*_path` is non-empty, with `detail` = the stored path
and a `present: bool`. Architect's call on the exact field.

**DEC-1 (my recommendation, security-relevant, orchestrator confirms).** The native dialog filters
to `*.exe` on Windows — **not** `*.cmd` / `*.bat`. Those run via `cmd.exe` with `%VAR%` argv
expansion (the architect's §8.4 residual); excluding them removes that residual for browsed
programs entirely, and every `.cmd` shim that matters (`code.cmd`) is a *detected* entry already.
macOS: `*.app` plus extensionless files. Linux: all files, backend enforces the execute bit.

**DEC-2.** `ToolSource` is **not** surfaced in the UI. `detail` already says everything the user can
act on (a path, or "built in"); a `registry` / `wellKnown` badge is implementation vocabulary.

**DEC-3.** `scannedAtMs` is **not displayed.** The architect's parenthetical ("the picker shows
'checked HH:MM'") is declined: the app has no time formatter (`grep` for
`toLocaleTimeString|formatTime` in `src/` → zero hits), a wall clock needs a per-minute re-render to
stay honest, and the user pressing Rescan already knows *when*. What they do not know is *what was
found* — so the note reports counts (§8, `SCAN_*`). `scannedAtMs` stays in the DTO as the
freshness identity the hook compares to know a refresh landed; AC10 is unaffected.

**`ToolPathLabel`, and why not `RefLabel`.** `RefLabel` is the §3.0-R3 component, but it delegates
to `splitPath` (`StatusFileRow.tsx:16`), which splits on `/` **only**. A Windows path
(`C:\Program Files\Microsoft VS Code\Code.exe`) therefore comes back as one leaf with `dir: null`,
`.ref-label-leaf` is `flex: none`, and the path overflows the popover instead of truncating.
**Widening `splitPath` is explicitly not the route**: it serves git paths, which are always `/`, and
loosening a shared parser to fix a display case in another subsystem is how a regression gets
planted in the status tree. `ToolPathLabel` owns the platform split, reuses the `.ref-label-*` CSS
so the truncation idiom stays one idiom, and never slices the string in JS (§3.0).

`SettingsExternalToolsSection.tsx` is 104 lines today and lands at ~150 — nowhere near the limit,
and no oversized file is touched.

## 4. The option model

### 4.1 Order — one list builder, both rows

1. `Auto-detect` (`value: ''`) — always first; the default and the ↺ target.
2. every `DetectedTool` for this kind, **in scan order** (catalog table order — deterministic, so
   the list never reshuffles between mounts).
3. ~~the **custom** entry (`value: 'custom'`), when `custom*Path` is non-empty.~~
   **SUPERSEDED 2026-09-15 (§16.1):** there is no `custom*Path` for the renderer to test. The custom
   entry **arrives inside `scan.terminals` / `scan.editors`** as the last element, already built by
   the backend, carrying `id: 'custom'`, a backend-derived `label`, `detail` = the sanitized path and
   `present: boolean`. The list builder does not construct it — it is item 2.
4. the **stale** entry, when the stored id is neither `''` nor `'custom'` nor in the detected list.
   *(Unchanged. Built from `scan.terminalLabels` / `scan.editorLabels`.)*

~~3 and 4 are mutually exclusive.~~ **Amended:** 3 is now part of 2, and 4 fires when the stored id
is absent from the list the backend sent — which now includes the custom row, so the two still
cannot both appear. There is no separator — `Combobox` has no separator concept and
adding one for a 2–8 row list is chrome for nothing.

### 4.2 Option fields

| Option | `label` | `hint` (detail line) | `disabled` |
|---|---|---|---|
| Auto-detect | `Auto-detect` | `Bonsai picks the first tool it finds` | no |
| detected, path source | `tool.label` | `<ToolPathLabel value={tool.detail} />` | no |
| detected, `detail === 'built in'` | `tool.label` | `Built in` | no |
| custom, `present: true` | `tool.label` (backend-derived) | `<ToolPathLabel value={tool.detail} />` | no |
| custom, `present: false` | `tool.label` | `Not installed` — §16.1 | no |
| stale | label from `scan.*Labels` | `Not installed` | **no** — see below |

> **AMENDED 2026-09-15 (§16.1):** the custom row's `label` and `detail` both come off the
> `DetectedTool` the scan sent — never from a settings field, and **never re-derived from the path by
> the renderer**. `detail` is display-only and already sanitized backend-side
> (`crates/bonsai-core/src/tools/custom.rs:358-369`: control/bidi chars stripped, truncated at 512
> chars **with a trailing `…`**), so it is not guaranteed to be a well-formed path and must not be
> parsed for anything but the last `/` or `\` that `ToolPathLabel` needs.

- `detail === 'built in'` is mapped to sentence-case `Built in` in the frontend. One `===` compare
  on a value the architect froze to exactly two forms (§2 of their contract). Cheaper than asking
  for a DTO change; if the architect prefers to send `"Built in"`, drop the mapping.
- **The stale entry stays enabled.** Disabling it greys the row the user is currently *on*, which
  reads as a broken control, and it would make the selection unrecoverable after the tool is
  reinstalled but before a Rescan. `Not installed` is a **word**, so the marker survives
  greyscale and needs no hue — WCAG 1.4.1 is satisfied without a badge.
- **Re-selecting the current value must not patch.** `ToolPickerRow`'s handler early-returns on
  `next === value`. Without it, re-picking the already-selected option fires a pointless
  `set_ui_settings` round trip on every row.

### 4.3 Two-line option rows — justified, because it is the one new pattern here

```
┌─────────────────────────────────────────────┐
│ ▍Visual Studio Code                         │  13px --text-1, ellipsis
│  C:\Program Files\Microsoft VS Code\Code.exe│  11px --text-2, head-ellipsized, leaf pinned
├─────────────────────────────────────────────┤
│  Windows Terminal                           │
│  Built in                                   │
└─────────────────────────────────────────────┘
```

`.combobox-option` is single-line today: `align-items: baseline; justify-content: space-between`
with `.combobox-option-hint { flex: none }`. That shape is correct for `checked out`
(`WorktreeCreateDialog.tsx:231`) and wrong for an absolute path: `flex: none` on a 46-char hint
collapses the label to nothing and then overflows the popover's 4px padding box.

**Alternative considered and rejected:** keep single-line options (label only) and show the selected
tool's path in the row note. It loses the one thing `detail` is *for* — telling two same-label
installs apart (the architect's OQ5) — at exactly the moment the user is choosing between them.

**Implementation: ancestor-scoped CSS, no new `Combobox` prop.** The section wraps each picker in
`<div className="tool-picker">`; the popover is `position: absolute` inside `.combobox` inside that
wrapper, so a descendant selector reaches it (§11). Option row height goes 27px → ~38px, so the
existing `max-height: 220px` popover shows ~5.5 rows and scrolls. That is fine for a 2–8 row list;
`max-height` is **not** changed.

## 6. Browse

**Placement:** right of the picker, inside the same stacked control cell. The picker is the primary
control and reads first; Browse is `btn-secondary`, 88px min width, and reads second. Two options
were rejected: a `Choose a program…` entry inside the popover (a `role="option"` that performs an
action instead of selecting a value — an a11y antipattern, and the user asked for a button), and an
overflow menu (chrome for a single action).

**Label:** `Browse…` — the house convention for "this opens a dialog"
(`Export session…`, `Delete logs…`, `Open repository…`).

**The perceptible delay is real and already has a house idiom.** The native dialog is opened by the
backend, so the click → dialog-visible gap is an IPC round trip plus OS window creation. Copy the
`SettingsDevLogsSection.tsx:88-99` `Export session…` treatment exactly:

- `aria-disabled={busy}` + `aria-busy={busy}` — **not** `disabled`.
- The **visible label does not change.** No `Browsing…`. Swapping a button's text mid-press
  re-announces it to AT and changes its width under the cursor, and the native dialog is itself the
  feedback the moment it appears.

- **B (Browse confirmed).** The visible channel is already complete — the picker's label becomes the

  do".
- **E (rescan landed).** The counts are **state**, not an outcome: `3 terminals and 4 editors found.`

report the AT user who pressed Browse or Rescan hears **nothing at all**, while the sighted user
watches the row change. That is P113 §8.1's "inline-only would make it visible-only, which is worse",
and this surface's version of §8.2's ruling that **placement is not an accessible carrier of
meaning**.

```
 *  complete in the row's own state (a landed rescan's counts, a confirmed Browse),
 *  where a second visible line would only restate it one step brighter. */
announceOnly(text: string): void;
```
Body is `report` minus `setNotes`: the same `announcedTextRef.current === text ⇒ flushSync(setAnnounce(''))`
dedup flush, then record the ref, then `setAnnounce(text)`.

announcer only ever becomes non-empty through `report`, which records what it wrote, so a non-empty
announcer showing `X` implies `ref === X`.* `announceOnly` obeys the identical discipline, so the
implication still holds — the proof is about **who may write the announcer and whether they record
it**, not about how many such functions there are. Two obligations follow and are MUST:
- The comment at `useOutcomeNotes.ts:59-79` says "the announcer goes non-empty ONLY through `report`".

- `announceOnly` **must not** reset `announcedTextRef` for any other reason, and `begin` still must
  not reset it (P113 §17.5).

(`useUiSettings.ts:291`, wired at `App.tsx:110/269`) is the app's existing **non-writing** adopt —

that it sets **every** field from disk, so a debounced patch for some *other* setting that has not
been written yet is reverted in the UI (the disk still gets it — P69b requeues). Narrow: it needs a
settings change within the debounce window and a Browse confirm in the same breath.

### 16.6 The strict-picker blank state — confirmed, and split

**Confirmed against the shipped control.** `Combobox.tsx:63-69`:
`selectedLabel = options.find(o => o.value === value)?.label ?? ''` and
`inputValue = query ?? selectedLabel`. A stored id whose label has not loaded renders **`''`**. The
`ui-reference.md` §12.13 bullet is exactly right, `placeholder` already exists on the control
(`:18`), and the prohibition on a synthetic "loading…" **option** stands — it would be selectable
and would patch a junk value, i.e. it would reintroduce the defect P112 exists to delete.

**But §5 state 7 conflates two windows, and the 2.1 s number makes the difference visible.**

- **7a — cold scan (`scan === null`).** No labels exist yet. At `''` the input reads `Auto-detect`
  immediately (a synchronous option). At any other value the input is **empty with
  `placeholder="Looking for installed tools…"`**. Row note `NOTE_SCANNING`. Picker enabled, Browse
  enabled, Rescan `aria-disabled` + `aria-busy`. The popover holds exactly **one** option.
- **7b — rescan (`scan !== null && scanning`). The placeholder must NEVER appear.** The previous
  scan's options are still in hand, so the input keeps the selected option's label and the popover
  keeps its list. Row note `NOTE_SCANNING`; everything else as 7a. **Blanking a control that already
  knows its own value for 2.1 s would be a regression introduced by a refresh button** — which is
  the general form of the rule and why it is going into `ui-reference.md` (§16.15).

Concretely: `useExternalToolScan` must hold the last good scan and **replace it only on a resolve**.
Never `setScan(null)` when a refresh starts, and never on a reject (§16.4 R5 depends on this too).

**Declined: preserving the popover highlight across a list that grows (a fifth `Combobox` change).**
Measured instead of assumed. `Combobox.tsx:82-91` resets `highlight` to `firstEnabled(filtered)`
whenever `filteredKey` — the joined value set — changes. Consequences:
- **7a, popover open when the scan lands:** the pre-scan list is one option, the highlight is on it,
  and the reset returns the highlight to the first enabled option — **the same one**. No user-visible
  effect.
- **7b, popover open when a rescan lands:** if the set is unchanged (the warm case), `filteredKey`
  is unchanged and there is **no reset**. Only a rescan that actually adds or removes a tool while
  the popover is open and the user has arrow-keyed off row 0 loses the highlight.
That residue is narrow enough not to justify touching a four-consumer shared control. Recorded as
known behaviour; `aria-activedescendant` follows `highlight`, so it stays consistent either way.

### 16.7 The 2.1 s cold scan — no new chrome, and no prefetch

**The measurement** (TODO.md, 2026-09-14): 55 PATH directories × 11 `PATHEXT` entries ≈ 4400 stats,
**2.1 s cold / 0.45 s warm**, and the `SCAN_REG_BUDGET` clock starts before any filesystem work, so
a cold first scan can spend the 1500 ms registry budget before the first `AppPaths` rung runs.

**Ruling: the opening state needs nothing beyond the placeholder.** 2.1 s does not change the house
idiom, it makes it load-bearing. The idiom is P113 §10.1's, verbatim: in-flight state is `aria-busy`
on the acting button plus a `…` line in the row's state note (`Deleting…`). Here that is
`NOTE_SCANNING` in each picker row and `SCAN_SCANNING` in the Rescan row — three labelled waits, all
in `aria-describedby`, plus the placeholder for the one case where the input itself cannot speak
(7a). No spinner, no skeleton, no progress bar: §10's reasoning holds a fortiori at 2.1 s, since the
Settings overlay can be open while the canvas graph is live.

**Declined: `aria-busy` on the picker input** (which would have been a fourth `Combobox` prop). It
would only ever be read by someone focused on the picker while a scan starts, and a scan can start in
exactly two ways: first mount (focus is on the pane, not the picker) or the Rescan button (focus is
on Rescan). In both, focus reaches the picker *after* the scan, where `describedBy` reads the note.
The prop would add API surface for a state no user can be in.

**Ruling: no prefetch, anywhere.** Two were considered:
- *On app start* — a 4400-stat IO burst competing with the first repo open, which is what the user
  actually launched the app to do. Detection is not repo state; it does not belong on that path.
- *On Settings open* — buys nothing. `SettingsShell.tsx:58` opens on `'general'` unless a deep link
  names another category, so Settings-open and General-mount coincide in the default case.

**What actually bounds the cost: it is once per process, not once per visit.** The backend caches the
scan and `useExternalToolScan` keeps a module-scoped cache (§3), so the 2.1 s is paid at most once
per app run, and only by a user who opens Settings. Every later visit to General is free, and a
rescan is 0.45 s warm — which is also why 7b's no-blank rule matters more than 7a's placeholder.

**Rescan while running:** label unchanged (`Rescan` — never `Rescanning…`; P113 and §6's rule),
`aria-disabled` + `aria-busy`, handler no-ops on a second press, state note `SCAN_SCANNING`, both
pickers in 7b. On landing: state note → `SCAN_COUNTS` / `SCAN_NONE`, `announceOnly` fires (§16.4 R3),
`aria-busy` drops, focus has never moved.

### 16.8 `scannedAtMs` — not displayed, and its only consumer is cache bookkeeping

DEC-3 stands: **no clock.** The app still has no time formatter, and a wall clock needs a per-minute
re-render to stay honest. §15's `Last checked 14:32 · …` alternative remains declined.

**But it needs a React consumer, and here is the job.** A warm rescan that finds the same tools
produces **no visible change at all** — same options, same counts sentence, same selection. A button
that visibly does nothing reads as broken, and the AT case is worse: writing the identical counts
string into the announcer is **silence**, because a live region fires on a text change (P113 §8.1).

So: **a landed refresh fires `announceOnly(SCAN_COUNTS)` unconditionally** — even when the counts are
byte-identical to the previous ones. The `''`-flush inside `announceOnly` (inherited from `report`)
is what makes the identical string announce a second time, and this is exactly **AC17's shape**: same
text, different event, must still produce a mutation. It is the strongest available argument for R2,
since the fallback (`report`) would produce a duplicate visible line on every press.

**Honest scope of the `scannedAtMs` answer, corrected on review.** The trigger for the announcement
is the **promise resolving**, not the timestamp: `ipc-api-tools.ts:13` guarantees `refresh: true`
advances `scannedAtMs`, so `next.scannedAtMs !== prev.scannedAtMs` is always true on a landed refresh
and a comparison would be doing no work. What the field is actually **for**, and the one job it has:
`useExternalToolScan` keeps a module-scoped cache across mounts (§3), so a **second** component or a
remount can tell a cached scan from a fresh one without re-fetching, and a late-arriving response
from a superseded call can be discarded by comparing against the newest `scannedAtMs` held. That is a
real consumer and it is why the field stays in the DTO — but it is **cache bookkeeping, not a UI
signal**, and I am not going to dress it up as one. **The answer to "does freshness get surfaced" is
still no**, by DEC-3, and the rescan announcement needs no timestamp to work.

Not displayed. Not formatted. Not in any user-visible string.

### 16.9 `PATHEXT` casing — accept it; normalise nothing in the renderer

**The finding is real and now precisely sourced.** `crates/bonsai-core/src/procutil_tests.rs:27-33`:
*"`PATHEXT` is conventionally UPPERCASE and Windows paths are case-insensitive, so a resolution built
from it carries the `PATHEXT` spelling (`code.CMD`) while the on-disk name is `code.cmd`. Both name
the same file and both spawn — and this is pre-existing behaviour."* So a subtitle will read
`C:\Users\…\bin\code.CMD`, `…\wt.EXE`, `…\pwsh.EXE`.

**Ruling: render `tool.detail` byte-identical. No case normalisation, no extension parsing, no
transform of any kind in the renderer.** Three reasons, in order of weight:

1. **The subtitle's whole job is to name the program Bonsai will spawn.** That is the string the
   resolver produced. A renderer that prettifies it shows something the backend never emitted, and if
   backend and display ever diverge for a *real* reason, the prettifier is what hides it.
2. **It is the transform the brief's second constraint forbids.** `detail` is display-only and
   backend-sanitized; "no UI may re-derive a label from the path" is the same rule one step down.
3. **`detail` is not reliably a path.** `sanitize_detail`
   (`crates/bonsai-core/src/tools/custom.rs:358-369`) strips disallowed characters and truncates at
   512 chars **with a trailing `…`**. A renderer parsing for "the extension after the last dot" would
   have to handle a string that ends mid-path in an ellipsis. `ToolPathLabel` splits on the last `/`
   or `\` for truncation and does nothing else — that is the maximum the renderer may know about this
   string.

**The honest fix is backend-side and is a follow-up, not a blocker:** report the on-disk directory
entry name instead of the `PATHEXT`-joined spelling. Cosmetic only — both spellings resolve and
spawn. Worth doing because a user comparing the subtitle against their own `where code` output
currently sees a mismatch that means nothing.

**Pinned, so nobody "fixes" it in the frontend later:** the default harness seam carries an
uppercase-extension detail, and **UA14** asserts the rendered subtitle is byte-identical to
`tool.detail`.

### 16.12 The scroll correction applies here, and the Rescan row is the measurement target

P113 §10.3 R1 relaxed the `scrollIntoView` ban for **"Dev slots only"** (condition 4). **Extend it to
this section's three slots**, with all four conditions and the `Math.ceil` step unchanged.

Why it transfers: the external-tools group is the **last group on General** and `general.rescan-tools`
is the **last row on the page** — structurally identical to `dev.delete-logs`, which is where AC2b's
clipping failure was found. The commit **adds a line and removes nothing**, and focus is still on the
acting control because Browse and Rescan are `aria-disabled`, not `disabled`. The Accounts ban's
reason — a commit that can remove the card under the pointer — does not exist here.

The step, restated so it cannot be half-implemented (P113 §10.3, and `ui-reference.md` §12.14):

1. Only when **measured**: the note's rect is not fully inside the scroll container's client rect.
2. `scrollIntoView({ block: 'nearest', behavior: 'auto' })` — instant, never `'smooth'`.
3. **Then the ceil correction:** `deficit = noteRect.bottom - paneClientRect.bottom`; while
   `deficit > 0`, `pane.scrollTop += Math.ceil(deficit)`. **`Math.ceil` is load-bearing:**
   `scrollIntoView` alone settles **0.171875 px** past the clip (reproduced at two viewports), and at
   DPR 1 the scroll offset snaps to whole pixels, so assigning the fractional deficit reads back
   unchanged. Without the ceil, AC2b **cannot be met by following the contract**.
4. Only while `document.activeElement` is inside the row that owns the slot.

**AC2b's target on this page is `general.rescan-tools`**, measured at the scroll position pressing
Rescan leaves behind — **not** after scrolling to the end of the pane, which is satisfiable by
construction and tests nothing.

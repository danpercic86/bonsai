# P112 — UI contract: external-tool pickers (detected list + Browse)

**Status:** spec — signed by `ui-designer` 2026-09-11. Implement with
`docs/contracts/P112-external-tool-detection.md` (behaviour authority) and
`docs/contracts/P112-tool-catalog.md` (candidate data).
**Replaces:** the two free-text rows in `src/components/SettingsExternalToolsSection.tsx` and the
`{path}`-vocabulary note at `:98-100`.
**Length:** ~520 lines, over the ~500 soft limit. Flagged, not trimmed — the overage is the state
table (§5) and the signed-copy table (§8), both of which are the deliverable. Split point if ever
needed: §8 into `P112-ui-copy.md`.

**Design position in one line.** The picker is the existing `Combobox`, in the existing stacked
settings row, beside a `btn-secondary` Browse — three patterns the app already ships. Nothing new
is invented except a two-line option row (§4.3) and one platform-path label component (§3).

## 0. What this contract needs from the architect — read first

The architect's file as of 2026-09-11 still states §8.2 / OQ2: *"there is deliberately no 'browse to
an executable' button"*. The orchestrator's brief supersedes that (user ruling, same day). The
amendments below are what the Browse button and the not-installed marker require. **Each is a data
shape I cannot design around; none is a preference.**

**AMEND-1 (blocking the not-installed state) — the scan must be able to name an undetected id.**
`ExternalToolScan` carries only *detected* tools, so a kept-but-stale selection (`editorTool:
'zed'`, zed absent) leaves the frontend holding an opaque id and no label. Rendering `zed` raw is
not house quality and `notepadpp` is not a word. Add to `ExternalToolScan`:

```rust
/// Display labels for EVERY catalog entry of this kind, ANY os — the picker still
/// OFFERS only `terminals` / `editors`. This exists solely so a selection that is
/// not currently detected can be named. Static `&'static str` data, no IO.
pub terminal_labels: BTreeMap<String, String>,   // id -> label
pub editor_labels: BTreeMap<String, String>,
```
All-OS coverage is required because `coerce_tool_id` deliberately keeps any-OS ids (§5.2 of the
architect's contract: settings.json may be synced between machines).
*Fallback if refused:* render the raw id in `var(--font-mono)` and the note as
`The editor you chose isn’t installed right now.` — a measurably worse state; take AMEND-1.

**AMEND-2 (blocking Browse) — `'custom'` as a pseudo-id plus a backend-write-only path.**
A browsed absolute path is not a catalog id, and `coerce_tool_id` maps anything unknown to `""`, so
the renderer cannot store it. Do **not** encode it as `terminalTool: "custom:C:\..."`: that value is
destroyed the moment the user picks anything else, and any renderer echo of the stored settings
(a full-state resend, a failed-patch requeue) coerces it to `""` — a silent loss. Instead:

| Wire key | Rust field | Written by | Meaning |
|---|---|---|---|
| `terminalTool` / `editorTool` | `terminal_tool` / `editor_tool` | renderer (coerced) | adds one legal value: `"custom"` |
| `customTerminalPath` / `customEditorPath` | `custom_terminal_path` / `custom_editor_path` | **`pick_external_tool` only** | absolute path the native dialog produced; **never** assigned from a patch |

`coerce_tool_id` accepts `"custom"` as a catalog-adjacent id and is otherwise unchanged. The two
path fields are absent from `UiSettingsPatch` entirely, so `set_ui_settings` has no way to reach
them — that is the whole security property, and it makes switching away from and back to `custom`
lossless. `picked("custom", kind)` rechecks the stored path (`is_file` + exec bit, or `is_bundle`)
and returns `None` when it is gone ⇒ auto ladder, identical to the stale-catalog-id case.

**AMEND-3 (blocking Browse) — the command.**
```rust
/// P112: open the NATIVE program picker and, on confirm, write `custom_*_path`
/// and `*_tool = "custom"` itself. The renderer cannot supply a path — it only
/// asks for the dialog. `Ok(None)` = the user cancelled: nothing is written.
#[tauri::command]
pub async fn pick_external_tool(kind: ToolKind) -> Result<Option<DetectedTool>, AppError>
```
Returns the resulting entry with `id: "custom"`, `source: "custom"` (new `ToolSource` variant),
`label` = the display name (macOS: bundle name minus `.app`; else the file stem — `Code`,
`sublime_text`, `nvim`), `detail` = the absolute path. Rejection is a single category error; the UI
never shows its text (§8, `BROWSE_ERR`).
**Sub-case to resolve, not for me:** when `*_tool == "custom"` but the stored path is gone, the UI
needs the path and the label to render the missing-custom state. Simplest: `list_external_tools`
always returns the custom entry when `custom_*_path` is non-empty, with `detail` = the stored path
and a `present: bool`. Architect's call on the exact field.

**DEC-1 (my recommendation, security-relevant, orchestrator confirms).** The native dialog filters
to `*.exe` on Windows — **not** `*.cmd` / `*.bat`. Those run via `cmd.exe` with `%VAR%` argv
expansion (the architect's §8.4 residual); excluding them removes that residual for browsed
programs entirely, and every `.cmd` shim that matters (`code.cmd`) is a *detected* entry already.
macOS: `*.app` plus extensionless files. Linux: all files, backend enforces the execute bit.

**DEC-2.** `ToolSource` is **not** surfaced in the UI. `detail` already says everything the user can
act on (a path, or "built in"); a `registry` / `wellKnown` badge is implementation vocabulary.

**DEC-3.** `scannedAtMs` is **not displayed.** The architect's parenthetical ("the picker shows
'checked HH:MM'") is declined: the app has no time formatter (`grep` for
`toLocaleTimeString|formatTime` in `src/` → zero hits), a wall clock needs a per-minute re-render to
stay honest, and the user pressing Rescan already knows *when*. What they do not know is *what was
found* — so the note reports counts (§8, `SCAN_*`). `scannedAtMs` stays in the DTO as the
freshness identity the hook compares to know a refresh landed; AC10 is unaffected.

## 1. The control: reuse `Combobox`, confirmed

`SettingsControlKind: 'combobox'` (`src/components/settings/types.ts:47-49`) with
`src/components/Combobox.tsx`, strict mode (`allowFreeInput` omitted ⇒ `false`). Confirmed against
the §12.3 table: >3 exclusive values, a set that grows with the catalog, values that need a
subtitle. `segmented` caps at 3. A native `<select>` cannot render a two-line option. Precedent in
Settings already exists: `appearance.graph-season` (`AppearanceCategory.tsx:98`).

**Strict mode is load-bearing here, not incidental.** Free-text entry is the defect P112 removes;
`allowFreeInput: false` means the input reverts to the selected option's label on blur/Escape and
`onChange` can only ever fire with an option's `value`. The control's own contract now enforces the
milestone's invariant.

Three small changes to `Combobox.tsx` (additive, no call site churn — all four existing users pass
strings and nothing else changes):

| Change | Why |
|---|---|
| `hint?: string` → `hint?: ReactNode` | the detail line must be a `ToolPathLabel`, not a string, to truncate a path correctly (§4.3). `ReactNode` ⊃ `string`, so `WorktreeCreateDialog` / `WhatChangedDialog` / `PrCreateForm` are untouched. |
| new `describedBy?: string` → `aria-describedby` on the input | the old `<input>` carried `aria-describedby={settingsRowHelpId(rowId)}` (`SettingsExternalToolsSection.tsx:70`). `Combobox` has no such prop, so every stateful note in §5 would be **silent to a screen reader** — a §12.2 violation. |
| new `title?: string` → `title` on the input | the closed input shows a truncated label; §3.0 requires truncation to be paired with a `title`. |

**Pre-existing SHOULD-FIX, same gap, not caused by P112:** `appearance.graph-season` has no
`aria-describedby`, so its help line is already unannounced. Fixing it is one prop at
`AppearanceCategory.tsx:98-104` once `describedBy` exists — do it in this increment while the file
is open.

| `src/components/settings/ToolPathLabel.tsx` | **new**, ~28 lines | leaf-preserving label for a **platform** path — splits on the last `/` **or** `\`, renders `.ref-label-head` + `.ref-label-leaf`. |

**`ToolPathLabel`, and why not `RefLabel`.** `RefLabel` is the §3.0-R3 component, but it delegates
to `splitPath` (`StatusFileRow.tsx:16`), which splits on `/` **only**. A Windows path
(`C:\Program Files\Microsoft VS Code\Code.exe`) therefore comes back as one leaf with `dir: null`,
`.ref-label-leaf` is `flex: none`, and the path overflows the popover instead of truncating.
**Widening `splitPath` is explicitly not the route**: it serves git paths, which are always `/`, and
loosening a shared parser to fix a display case in another subsystem is how a regression gets
planted in the status tree. `ToolPathLabel` owns the platform split, reuses the `.ref-label-*` CSS
so the truncation idiom stays one idiom, and never slices the string in JS (§3.0).

`SettingsExternalToolsSection.tsx` is 104 lines today and lands at ~150 — nowhere near the limit,
and no oversized file is touched.

## 4. The option model

### 4.1 Order — one list builder, both rows

1. `Auto-detect` (`value: ''`) — always first; the default and the ↺ target.
2. every `DetectedTool` for this kind, **in scan order** (catalog table order — deterministic, so
   the list never reshuffles between mounts).
3. the **custom** entry (`value: 'custom'`), when `custom*Path` is non-empty.
4. the **stale** entry, when the stored id is neither `''` nor `'custom'` nor in the detected list.

3 and 4 are mutually exclusive. There is no separator — `Combobox` has no separator concept and
adding one for a 2–8 row list is chrome for nothing.

### 4.2 Option fields

| Option | `label` | `hint` (detail line) | `disabled` |
|---|---|---|---|
| Auto-detect | `Auto-detect` | `Bonsai picks the first tool it finds` | no |
| detected, path source | `tool.label` | `<ToolPathLabel value={tool.detail} />` | no |
| detected, `detail === 'built in'` | `tool.label` | `Built in` | no |
| custom | `tool.label` (file stem / bundle name) | `<ToolPathLabel value={path} />` | no |
| stale | label from AMEND-1 | `Not installed` | **no** — see below |

- `detail === 'built in'` is mapped to sentence-case `Built in` in the frontend. One `===` compare
  on a value the architect froze to exactly two forms (§2 of their contract). Cheaper than asking
  for a DTO change; if the architect prefers to send `"Built in"`, drop the mapping.
- **The stale entry stays enabled.** Disabling it greys the row the user is currently *on*, which
  reads as a broken control, and it would make the selection unrecoverable after the tool is
  reinstalled but before a Rescan. `Not installed` is a **word**, so the marker survives
  greyscale and needs no hue — WCAG 1.4.1 is satisfied without a badge.
- **Re-selecting the current value must not patch.** `ToolPickerRow`'s handler early-returns on
  `next === value`. Without it, re-picking the already-selected option fires a pointless
  `set_ui_settings` round trip on every row.

### 4.3 Two-line option rows — justified, because it is the one new pattern here

```
┌─────────────────────────────────────────────┐
│ ▍Visual Studio Code                         │  13px --text-1, ellipsis
│  C:\Program Files\Microsoft VS Code\Code.exe│  11px --text-2, head-ellipsized, leaf pinned
├─────────────────────────────────────────────┤
│  Windows Terminal                           │
│  Built in                                   │
└─────────────────────────────────────────────┘
```

`.combobox-option` is single-line today: `align-items: baseline; justify-content: space-between`
with `.combobox-option-hint { flex: none }`. That shape is correct for `checked out`
(`WorktreeCreateDialog.tsx:231`) and wrong for an absolute path: `flex: none` on a 46-char hint
collapses the label to nothing and then overflows the popover's 4px padding box.

**Alternative considered and rejected:** keep single-line options (label only) and show the selected
tool's path in the row note. It loses the one thing `detail` is *for* — telling two same-label
installs apart (the architect's OQ5) — at exactly the moment the user is choosing between them.

**Implementation: ancestor-scoped CSS, no new `Combobox` prop.** The section wraps each picker in
`<div className="tool-picker">`; the popover is `position: absolute` inside `.combobox` inside that
wrapper, so a descendant selector reaches it (§11). Option row height goes 27px → ~38px, so the
existing `max-height: 220px` popover shows ~5.5 rows and scrolls. That is fine for a 2–8 row list;
`max-height` is **not** changed.

## 5. States — every one, both themes

Row height never changes between states: the note is always exactly one `<p>` in the help slot, and
it holds `min-height: 16px` so a one- to two-line change is the only movement (the 56ch cap means
the longest string below wraps to 2 lines; the row grows 16px and nothing overlaps).

| # | State | Closed picker reads | Note (§8 id) | Other |
|---|---|---|---|---|
| 1 | **auto-detect** (`''`), ≥1 detected | `Auto-detect` at `--text-1` — a real option label, **not** a placeholder | `NOTE_AUTO` | ↺ **absent** (value == default) |
| 2 | **auto-detect, nothing detected** | `Auto-detect` | `NOTE_NONE` | picker stays enabled (Auto-detect is still an option, Browse still works). Popover shows exactly one option — the note is what explains it |
| 3 | **detected tool selected** | the tool label | `NOTE_PATH` (path in `.mono`) or `NOTE_BUILTIN` | ↺ present |
| 4 | **custom (browsed) path** | the file stem / bundle name | `NOTE_PATH` | ↺ present; identical treatment to 3 by design — a browsed tool is not second-class |
| 5 | **selected, not installed** (stale catalog id) | the tool label, unchanged | `NOTE_STALE` | ↺ present. Popover marks the entry `Not installed`. Selection **kept**; launch silently uses the auto ladder (user ruling) |
| 6 | **custom path gone** | the stored label | `NOTE_STALE_CUSTOM` | as 5; needs the AMEND-3 sub-case |
| 7 | **scanning** (initial mount, or Rescan in flight) | at `''`: `Auto-detect`. **At any other value: empty, with `placeholder="Looking for installed tools…"`** — see below | `NOTE_SCANNING` | picker **enabled** (the stored selection is still valid); Browse enabled; Rescan `aria-disabled` + `aria-busy` |
| 8 | **browse in flight** | unchanged | note unchanged | Browse `aria-disabled="true" aria-busy="true"`, label unchanged (§6) |
| 9 | **browse cancelled** | unchanged | unchanged | nothing happens, no message. A cancel is not an error |
| 10 | **browse rejected** (not a program) | unchanged | note unchanged; `BROWSE_ERR` appears as a **second** paragraph in the same help slot, warning treatment (§11) | cleared on the next Browse or pick |

**State 7's blank input is structural, not a bug to hide.** `Combobox` strict mode derives the
input's text from `options.find(o => o.value === value)?.label`, and before the scan lands the only
option is `Auto-detect` — the AMEND-1 label map arrives *with* the scan. So a stored
`editorTool: 'vscode'` has no label yet and the input renders empty. Do not paper over it with a
synthetic "loading" option (it would be selectable and would patch garbage). Pass
`placeholder="Looking for installed tools…"` (the prop already exists) whenever
`scanning && value !== ''`; at `''` the input reads `Auto-detect` immediately because that option is
synchronous. Under `?tools=slow` this is visible for 1200 ms and must read as "loading", not as
"empty setting".
| 11 | **hover** (picker) | — | — | `.dialog-input` unchanged (no hover rule today); option rows `.combobox-option--active` via `onMouseEnter` |
| 12 | **focus-visible** | — | — | 2px `--accent`, `outline-offset: 1px` on the input and on Browse/Rescan (§9) |
| 13 | **disabled** | — | — | never happens for these rows; no gate above them, so no §12.12 gate note |
| 14 | **long label / deep path** | label ellipsizes at the control's right edge + `title` holds the full string | `NOTE_PATH` wraps within 56ch, path in `.mono` with `title` | option detail line: head ellipsized, leaf pinned (§4.3) |

**Both themes.** No state uses a colour not already theme-paired. Contrast on `--bg-0`, worst case
per pair: label `--text-1` 13.6:1 dark / 12.4:1 light; note and detail `--text-2` 6.9:1 dark /
7.6:1 light (AA text ✓); `.combobox-option-hint` on `--selection` 5.01:1 dark / 6.42:1 light
(already measured and signed in P100, `dialogs-forms.css:266-271`); the input's 1px `--border`
edge is decorative delineation, and the 28px control's meaning carriers are its text and its focus
ring, not the border. `BROWSE_ERR` uses the signed P107 recipe — `--text-1` ink on a 12%
`--warning` tint with a 3px `--warning` bar: ink 12.0:1 / 11.7:1, bar 4.96 / 3.38 (graphics ✓).
**No new token is introduced.**

## 6. Browse

**Placement:** right of the picker, inside the same stacked control cell. The picker is the primary
control and reads first; Browse is `btn-secondary`, 88px min width, and reads second. Two options
were rejected: a `Choose a program…` entry inside the popover (a `role="option"` that performs an
action instead of selecting a value — an a11y antipattern, and the user asked for a button), and an
overflow menu (chrome for a single action).

**Label:** `Browse…` — the house convention for "this opens a dialog"
(`Export session…`, `Delete logs…`, `Open repository…`).

**The perceptible delay is real and already has a house idiom.** The native dialog is opened by the
backend, so the click → dialog-visible gap is an IPC round trip plus OS window creation. Copy the
`SettingsDevLogsSection.tsx:88-99` `Export session…` treatment exactly:

- `aria-disabled={busy}` + `aria-busy={busy}` — **not** `disabled`.
- The **visible label does not change.** No `Browsing…`. Swapping a button's text mid-press
  re-announces it to AT and changes its width under the cursor, and the native dialog is itself the
  feedback the moment it appears.
- The click handler no-ops while busy (`if (!busy) onBrowse()`), which is what `aria-disabled`
  requires — the button is still focusable and still in the tab order.
- **No spinner.** A spinner for a ≤400ms gap that ends in an OS window is noise, and §"Motion"
  forbids anything that can contend with the graph render budget.

`aria-disabled` over `disabled` is the load-bearing choice: a `disabled` button loses focus, and
the browser moves focus to `<body>`. Keeping it focusable means **focus is still on Browse when the
native dialog closes**, so cancel needs no focus-restore logic at all.

**On cancel** (`Ok(None)`): nothing is written, no message, no toast, note unchanged, focus stays on
Browse. **On confirm:** the backend has already persisted; the hook applies the returned
`DetectedTool` to local `UiSettings` state directly and fires **no patch** (a renderer patch
carrying a path is exactly what P112 forbids). The row switches to state 4. **On rejection:** state
10.

**Why the error is inline and not a toast.** `.toast-stack` is `z-index: 90` and `.dialog-overlay`
is 100 (§10.2) — Settings is a dialog, so a toast raised from it renders *behind* the card. Every
other Settings section reports inline.

`BROWSE_ERR` therefore lives in that row's help slot as a **second paragraph beside** the state
note — not as a replacement for it. §12.2 sanctions exactly this ("a note plus a conditional
caveat"), the note is still true while the error shows (`Runs C:\…\Code.exe.` did not stop being
true because a *different* file was rejected), and the control names both ids space-separated. The
error `<p>` is the §12.3.4 shape: **permanently present, empty text when idle**, so the live region
exists in the a11y tree before it has anything to say. It collapses to zero height when empty
(§11) and is cleared on the next Browse or pick.

## 7. Rescan

One Rescan for the section, not one per picker: `list_external_tools` returns both lists in a single
round trip, so two buttons would be two names for one action.

A catalogued **button row** (`general.rescan-tools`), the `Show tour` / `Delete all log files`
pattern: `rowLabel` is the visible row title, the catalog `label` is the button text and the
button's accessible name. This buys search coverage, the row grid, and an announced name for free —
a bare button under the group would have to self-filter (§12.5) and would carry no help.

- Button `btn-secondary`, `min-width: 72px` (`.settings-toggle-btn`), right-aligned.
- **Pass `rowLabel`, never `controlId`.** `SettingsRow` emits `<label for={controlId}>`, and
  `<button>` is a labelable element — so a `controlId` would make the button's accessible name
  `Detected tools`, contradicting the catalog `label: 'Rescan'` and failing the coverage guard.
  `SettingsDevLogsSection.tsx:74` is the precedent: `rowLabel` alone.
- The button carries `aria-describedby={settingsRowHelpId('general.rescan-tools')}` so its note is
  part of its description, not a sentence only sighted users get.
- `aria-disabled` + `aria-busy` while scanning; label unchanged (same rule as Browse).
- No ↺ (nothing to reset), so the row carries no `reset` descriptor; its 24px column stays reserved.
- The note reports **counts, not a clock** (DEC-3): `SCAN_COUNTS` / `SCAN_SCANNING` / `SCAN_NONE`.
- Scan trigger: on the hook's first mount only. No timer, no focus rescan — detection is not repo
  state (the architect's §3).

## 9. Interaction, keyboard, accessibility

**Tab order** (pure DOM order, no `tabindex` beyond the rail's roving one):
`Terminal picker → Terminal Browse → [Terminal ↺] → Editor picker → Editor Browse → [Editor ↺] → Rescan`.
The ↺ sits in grid column 2 / row 1 of a stacked row but after the control in the DOM — that is the
existing `SettingsRow` order and is not changed here.

**Picker keyboard** (all already in `Combobox`): `↓`/`↑` open the popover, then move the highlight
skipping disabled rows; `Enter` selects the highlighted option; `Esc` closes the popover **only**
(capture-phase window listener, `stopImmediatePropagation`) and reverts the typed query — a second
`Esc` reaches Settings' own layered handler and closes the dialog; typing filters on option label;
`Tab`/blur closes and reverts. Free text can never be committed (strict mode). **Enter never
closes Settings** — settings apply live (§12.4).

**Roles and names.** `role="combobox"` + `aria-expanded` / `aria-controls` / `aria-autocomplete="list"`
/ `aria-activedescendant` on the input; `role="listbox"` on the popover; `role="option"` +
`aria-selected` + `aria-disabled` per row. The input's accessible name comes from the row's
`<label for>` (`SettingsRow` emits it when `controlId` is passed) — `Terminal` / `Editor`, unique in
the dialog. **Do not also pass `ariaLabel`**; two naming sources on one control is how the
`Git config , repository` defect (§11) happened.

**What a screen reader announces for "not installed".** Two independent carriers:
1. In the popover, the option's accessible name is the label plus the detail line — `Sublime Text
   Not installed`, because the two spans are both in the option's name computation. Hence
   `Not installed` is a phrase, not an icon.
2. On the closed control, the **note** carries it: `describedBy={settingsRowHelpId(rowId)}` points
   the input at the note element, so focusing the picker announces
   `Terminal, combobox, Sublime Text, Sublime Text isn’t installed right now. “Open in terminal”
   falls back to auto-detect; your choice is kept.` This is exactly why `describedBy` (§1) is not
   optional — without it the whole state table is silent.

**Live regions — exactly two in the section, and deliberately not five.** A scan landing changes
*both* picker notes and the Rescan note in the same tick, so making all three live would queue three
sentences for one event. Therefore:

- **The Rescan row's note is the only live region for scan results** (`aria-live="polite"`). One
  event, one announcement: `3 terminals and 4 editors found.`
- **The two picker notes are description-only** — not live. They are announced on focus via
  `describedBy`, which is where a user who cares about a specific row will hear them.
- **Each picker row additionally holds one permanently-present, empty-when-idle
  `<p aria-live="polite">` for `BROWSE_ERR`** (the §12.3.4 draft-hint shape). A live region mounted
  in the same tick as its text is not announced, which is why it is always in the DOM. The picker's
  `aria-describedby` **composes both ids** space-separated (`{rowId}-help {rowId}-browse-error`) and
  never replaces the note's — §12.2: everything visible in the help cell is in the description.
- **No `role="alert"` anywhere.** Nothing in this section interrupts: a rejected file is a
  correction the user is about to retry, not a failure of something they had already finished.

**Hit targets** (§3.1, ≥24px, both themes, both densities): picker input 28px tall, Browse and
Rescan `btn-secondary` ≥28px, ↺ 24×24. The option rows are ~38px.

**Focus rings:** 2px `--accent`, `outline-offset: 1px`, `:focus-visible` only, on the picker input,
Browse, Rescan and ↺. See §11 for the one CSS rule the picker needs to get this (the shared
`.dialog-input:focus` sets `outline: none`).

**Focus across the native dialog:** `aria-disabled` keeps Browse in the tab order and focused, so
there is nothing to restore. Whether WebView2 / WebKit / WebKitGTK actually return
`document.activeElement` to the button after an OS modal closes is per-platform and cannot be
verified headless — **USER CHECKPOINT UC-UI-2**.

**Command palette:** no new entries. These are configuration, reached by `Ctrl/Cmd + ,` and then
search — the existing `Open Settings` action plus the §12.5 row search already cover them, and the
palette is at ~150 commands (restraint over addition). The *actions* these settings configure
(`Open in terminal` / `Open in editor`) are already in the palette and unchanged.

**`prefers-reduced-motion`:** nothing to honour — see §10.

## 10. Motion

None is added. The popover appears and disappears with no transition (existing `Combobox`

no state in §5 is carried by colour alone.
**UA7** Both `Browse…` buttons have distinct accessible names, each containing `Browse`; both
Rescan and Browse stay focusable while busy (`aria-disabled`, not `disabled`).

## 2. The dock bar — determinate when a fraction is known

### 2.1 Which run drives it

`activeRun` (already a prop; `useGitActivity.ts:233` = the **newest** running run). The bar is
determinate **iff** `progressFraction(activeRun) !== null` — in practice a fetch/pull/`cloneRepo`
in its `network` phase with `totalObjects > 0` (clone progress arrives through the architect's
§2.5 forwarder). Every other case — preparing, hooks, push network,
finalizing, every §4 operation, a fetch before its first count — is the indeterminate sweep.

Overlap (auto-fetch running, user checks out a branch): `activeRun` is the checkout, so the bar
sweeps. That is correct — the bar describes the thing the user just did; the fetch's counts remain
readable in its own row's sub-label. No "pick the run that has a fraction" logic.

### 2.2 Markup (`src/components/GitActivityDock.tsx:167`)

```
<div class="git-dock-progress" aria-hidden="true"
     data-determinate?="true"            ← only when fraction !== null
     style="--progress: <0..1>">         ← only when fraction !== null, clamped to [0, 1]
```

Derived locally in the dock from `activeRun` — **no new prop**. Clamp because `receivedObjects` can
momentarily exceed `totalObjects` on some servers; an overflowing `scaleX` would paint past the
right edge.

### 2.3 CSS (`src/styles/git-dock.css`, replacing `:45-52`)

```css
/* P119 §2.3 — determinate mode: a full-width fill scaled by transform (no layout). */
.git-dock-progress[data-determinate]::after {
  animation: none;
  width: 100%;
  transform-origin: left center;
  transform: scaleX(var(--progress, 0));
  transition: transform 150ms ease-out;
}

/* P119 §6 — sub-perceptual ops get a row, never a one-frame flash of bar. */
.git-dock-progress {
  animation: git-dock-progress-reveal 0s linear 150ms both;
}

@keyframes git-dock-progress-reveal {
  from { opacity: 0; }
  to   { opacity: 1; }
}
```

(The reveal is a 0-duration step after a 150ms delay — an appearance delay, not motion.)

Geometry, colour and placement unchanged: 2px, `--accent`, absolutely positioned on the dock's top
edge, `pointer-events: none`, shown in **both** collapsed and expanded states. Contrast of the fill
against the dock edge is the existing shipped pair (§5 below).

### 2.4 Reduced motion (`src/styles/reduced-motion.css`)

Keep the existing `.git-dock-progress::after` rule (sweep → static 100% at 0.6 opacity). Add:

```css
  /* P119: the determinate fill snaps to each new fraction, and reads at full
     strength so a partial fill is distinguishable from the static sweep. */
  .git-dock-progress[data-determinate]::after {
    transition: none;
    opacity: 1;
  }
```

The `git-dock-progress-reveal` delay is **not** disabled under reduced motion (it is not motion).

### 2.5 A11y

The bar stays `aria-hidden`. It is never the only carrier: the dock header's `.git-dock-detail`
(`· 12,340 / 50,000 objects`) and the toolbar readout carry the same fact in words, and the live
region still announces phases/terminals only — never progress ticks (P87 §6, unchanged).

## 3. Refresh — the glyph rotates

### 3.1 When

While `refreshing === true` (`RepoWorkspace.tsx:182,1051-1062` — set **only** by the manual
refresh: the button, `Ctrl/Cmd+R`, `F5`). Watcher-driven and window-focus rescans do **not** spin —
they are background upkeep and would make the icon twitch on every alt-tab. The spin is scoped to
`refreshing`; the button's other three disabled causes (`statusLoading`, `graphLoading`,
`mutating`) stay a plain disabled button.

**Minimum visible duration: 600ms** (one full turn). A manual refresh on a small repo resolves in
~50ms, which would render as a 30° twitch that reads as a glitch. Implement as a tiny hook
`src/components/repoWorkspace/useMinimumBusy.ts` — `useMinimumBusy(busy: boolean, minMs: number):
boolean` (true on the rising edge, falls no earlier than `minMs` after it). Pure timing; no IPC. The
button's `disabled` keeps following the raw `refreshing` (never block input for cosmetics).

### 3.2 Markup (`WorkspaceToolbar.tsx:278-287`)

- `aria-busy={spinning ? 'true' : undefined}` on the `<button>`.
- `title`: `Refreshing…` while spinning; otherwise the existing `Refresh (Ctrl+R)` /
  `Refresh (⌘R)` from `shortcutLabel('Mod+R')`.
- `aria-label` stays **`Refresh`** in both states — the accessible name must not change mid-op
  (announcer churn, and a name change on a focused control is re-announced by NVDA).
- No live-region announcement: the refresh result is the refreshed UI; the dock announcer is for
  git runs only.

### 3.3 CSS — `src/styles/controls.css`, directly after the `.toolbar-right .btn-icon svg` rule (`:268-272`)

```css
/* P119 §3 — manual refresh in flight: the glyph rotates and takes the accent.
   The button is disabled for the same span, so the colour must override
   .btn-icon:disabled's --text-3 (which is a sanctioned-role grey, not a state cue). */
.toolbar-refresh[aria-busy='true'] {
  color: var(--accent);
}

.toolbar-refresh[aria-busy='true'] svg {
  animation: toolbar-refresh-spin 600ms linear infinite;
}

@keyframes toolbar-refresh-spin {
  to { transform: rotate(360deg); }
}
```

- **Placement is load-bearing.** `.toolbar-refresh[aria-busy='true']` and `.btn-icon:disabled`
  (`controls.css:172`) have the same specificity (0,2,0), so the accent wins only because it comes
  **later in `controls.css`**. Do not move it to `tabs.css`, where `.toolbar-right` lives.
- **Motion rule.** Transform-only, compositor-thread, 16px glyph — no layout, no canvas contention.
  The ≤150ms rule governs *transitions*; a continuous busy indicator follows the existing
  `header-progress-sweep` precedent (1.1s infinite). This is a **user-ruled exception** to
  `ui-reference.md` §8 "words, never spinners", scoped to this one glyph; §8 is updated to say so.
- **Reduced motion** (`reduced-motion.css`): `.toolbar-refresh[aria-busy='true'] svg { animation:
  none; }`. The `--accent` colour remains, so the busy state is still visible without motion
  (and the title says `Refreshing…`).
- **Contrast** (glyph = UI graphic, needs ≥3:1 on the toolbar's `--bg-1`): `--accent` on `--bg-1` =
  **5.07:1 dark** (`#4f8cff` / `#1d2026`), **4.34:1 light** (`#2f6fe4` / `#f6f7f9`). Hover does not
  apply (the button is disabled).
- Both densities: the toolbar has no density variant; the 32px box and 16px glyph are unchanged.
- Focus: if the button had focus when clicked, it becomes disabled and focus falls to `<body>` —
  **pre-existing** behaviour, not introduced here; flagged as SHOULD-FIX follow-up (§9, still-open item 1).

## 4. Row copy for every new operation

### 4.1 How the existing formatter composes a row (unchanged mechanics)

- **Visible row / collapsed bar:** `glyph · noun (600, --text-1) · target (11px mono, --text-2,
  RefLabel 22ch) · pill · duration · HH:MM`. The visible row stays **preposition-free** (P87b FU-1
  §3.2). For every operation below this reads like the git command line — `Merge feature/x`,
  `Rebase main`, `Cherry-pick a1b2c3d`, `Checkout main` — which is why no preposition is needed on
  screen.
- **Accessible name + announcer:** `nounWithTarget` / `verbWithTarget` join with a preposition.
  `Rebase onto main — success, 0.4 seconds, 14:32`; announcer `Rebase onto main finished — success`
  / `… failed`.
- **Running sub-label:** `objectsReadout ?? phaseLabel(category, phase)`.

### 4.2 Required changes to the formatter

1. **Move the category table out of `gitActivityFormat.ts`** (321 lines; ~45 new entries would cross
   the 500-line limit) into a new static-table module **`src/components/gitActivityCategories.ts`**:
   `CATEGORY_META` + `TARGET_PREPOSITION` + the per-category flags below. `gitActivityFormat.ts`
   imports from it; `categoryMeta()` keeps its signature and location so no caller changes.
2. **Extend `CategoryMeta`:**
   - `blockedNoun: string` — the lowercase object in the blocking-hook note (`This hook blocked the
     {blockedNoun}.`). Replaces `opNoun()` in `GitActivityRow.tsx:38-42`, which falls through to
     `commit` for any unknown category (a blocked rebase would read "blocked the commit").
   - `countNoun?: (n: number) => string` — only `deleteBranches` and `discard`, the two categories
     that carry `targetCount` (§4.4).
   - `networkLabel?: string` — the `network`-phase string for the few new ops that talk to a remote.
   - `family` is **not** a field; the glyph is the family (§5). (Rev 1's `quiet` flag is dropped:
     its only members, stage/unstage, are not logged.)
3. **Widen `TARGET_PREPOSITION`** from `'to' | 'from' | 'on'` to
   `'to' | 'from' | 'on' | 'onto' | 'into' | 'in' | 'at' | 'for' | null`, where `null` = direct object
   (`Merge feature/x`, no joining word). Keep it an exhaustive `Record<Category, …>` so tsc forces a
   choice for every new category.
4. **`phaseLabel` rule for new categories** (the seven existing categories keep their LOCKED P87 §1
   rows byte-for-byte): `preparing` and `finalizing` → `meta.participle`; `network` →
   `meta.networkLabel ?? meta.participle`; `runningHook` → unchanged (`Running <hook> hook…`).
   Rationale: for a 3s checkout on a big repo, `Preparing…` claims the work has not begun; the
   participle is the truthful label. Implement as a default branch, not 40 case lines.
5. **`durationLabel` floor:** `ms < 100` → `<0.1s`; `durationWords` → `under 0.1 seconds`. Instant ops
   otherwise read `0.0s`, which looks like "did not run".
6. **Empty-dock hint** (`GitActivityDock.tsx:204`) — replace
   `Fetch, pull, push, or commit and it will show up here.` with
   **`Every change Bonsai makes to this repository shows up here.`** Title unchanged.

### 4.3 The copy table

Columns: **Wire** = the architect's §1 `GitActivityCategory` string (the table key).
**Noun** = visible row + collapsed bar. **Verb** = announcer (`{Verb} {prep} {target}
finished — success`). **Participle** = busy button label where one exists, and the running
sub-label per §4.2-4. **Prep** = accessible-name joiner (`—` = `null`, direct object).
**Target** = the raw identifier the backend sends on `started` (P87b FU-1 §3.6 guarantees apply: raw
git identifier, set once, immutable, sanitized by the backend funnel). **⚑** = can stop on conflicts
(§4.5). Short SHA = 7 hex chars, always.

**This revises P87b FU-1 §3.6-1's exhaustive shape list.** Besides `<remote>/<branch>`, `<remote>`,
and a branch short name, `target` may now also be: a 7-char short SHA, `stash@{n}`, a tag name, a
remote name, a repo-relative path (file or submodule), or a worktree name. Every other §3.6
guarantee is unchanged — a raw identifier, never a phrase, set on `started`, immutable, and passed
through the backend's sanitizing funnel.

the run is recorded by the mounted workspace's dock — e.g. cloning a second repo while repo A is
open adds `Clone my-project` to A's dock. From the no-repo screen there is no dock and no row;
`CloneDialog`'s own `progress.clone-progress-bar` stays the feedback there. Whether the row survives
switching to the newly cloned repo depends on whether the workspace (and its session log) remounts;
either behaviour is acceptable and neither needs special-casing (events carry no repo id —
architect §7 note).

### 4.4 Multi-target operations (a count is not an identifier)

A delete of three branches has no legal `target` (P87b FU-1 §3.6-1: a raw identifier, never a
phrase). **Confirmed by the architect (§2.7):** `started.targetCount?: number`, present iff the run
acts on ≥2 items, and then `target` is absent; the key is absent (not `null`) below 2. Only
`deleteBranches` and `discard` ever carry it. The frontend then renders `meta.countNoun(n)` **in the noun slot** (600, `--text-1`) and nothing in the
target slot: row `Delete 3 branches`, name `Delete 3 branches — success, 0.1 seconds, 14:32`,
announcer `Delete 3 branches finished — success`. `n` is formatted with `toLocaleString()`. Same
precedent as `all remotes`: the backend sends a fact, the frontend owns the words.

**Frontend loops stay N runs.** Where the UI calls a single-item command once per item (e.g. several
tags deleted in turn), each call is its own run and its own row — batching those is an architect
non-goal (§10-7). Accepted: these are rare, deliberate actions, and one row per real git change is an
honest record.

### 4.5 Stopped on conflicts — a third terminal status (user ruling; architect §2.6)

Merge, rebase*, cherry-pick*, revert*, stash apply/pop, and checkout / create-branch-here when their
stash re-apply conflicts (⚑ above) routinely **stop with conflicts**.
That is neither `Success` (the op did not complete) nor `Failed` (nothing went wrong; the user now
has work to do). Logging it as `⚠ Failed` would be a false alarm on the most common rebase outcome.

Wire: `finished{success: true, outcome: 'conflicts'}`; the reducer derives status `conflicts`
(architect §4.3). Pill **`! Conflicts`**, §11 recipe with
`--h: var(--warning)` (the same hue as the AI dock's `? Needs you`), label `--text-1`, glyph
`aria-hidden`. Accessible name `Merge feature/x — conflicts, 0.3 seconds, 14:32`; announcer
**`Merge feature/x stopped — conflicts to resolve`**. `hasTerminalRuns` / `pruneGitRuns` treat it as
terminal. CSS: one selector added beside the existing pill hue rules in `git-dock.css` —
`[data-status='conflicts'] { --h: var(--warning); }` — and `GitStatusPill['dataStatus']` gains
`'conflicts'`. A conflicts run shows **no** §4.7 outcome detail — the pill already says it.

### 4.7 Outcome detail — fast-forwarded / merged / up to date (user ruling; architect §2.6)

A successful run may carry `outcome` `fastForwarded` | `merged` | `upToDate` (on `merge`, the
`rebase` family, and `checkoutBranch`'s auto fast-forward). It renders as a detail span in the
existing `.git-run-subphase` slot (same class, same 11px `--git-dock-meta`, same `flex-shrink: 3`),
which today is empty on terminal rows, and in the collapsed bar's `.git-dock-detail` slot as
`· <detail>`:

| `outcome` | Detail (visible) | Accessible-name clause | Announcer |
|---|---|---|---|
| `fastForwarded` | `Fast-forwarded` | `fast-forwarded` | `Merge feature/x finished — fast-forwarded` |
| `merged` | `Merge commit created` | `merge commit created` | `Merge feature/x finished — merge commit created` |
| `upToDate` | `Already up to date` | `already up to date` | `Merge feature/x finished — already up to date` |
| absent | nothing | nothing | `… finished — success` (unchanged) |

Accessible name: the clause goes after the status word —
`Merge feature/x — success, fast-forwarded, 0.2 seconds, 14:32`. The same three strings serve the
rebase and checkout rows (`Rebase onto main finished — already up to date`). Implemented as one
`outcomeLabel(outcome)` formatter in `gitActivityFormat.ts`; no per-category copy.

### 4.6 Failures

- The existing failure toast (`Couldn't <verb> <target>. <remedy>`, §8) is **unchanged**; the dock
  row is the record, the toast is the alert.
- libgit2-backed ops produce no process output, so a failed checkout's expanded log would read
  `No output.` — useless. **Confirmed (architect §2.8):** the backend emits the user-facing
  `AppError::message()` (the same sentence the toast shows; never raw libgit2 text) as a final
  `stderrLine` before `finished{failed}`. The row shows it with the existing stderr cue (2px
  `--warning` left border, `stderr:` sr-only prefix). **Exception: `hookRejected`** gets no reason
  line — its hook output is already on the stream, and the blocking-hook note (§4.2-2) names it.
- A **cancelled** confirmation (user pressed Cancel in the Hard-reset / Delete-branch dialog) emits
  **no run** — `started` fires only after confirmation. Nothing happened, so nothing is logged.

## 6. Instant ops flooding the dock — resolved

The user ruling removes the flood source: stage/unstage (and conflict-resolution writes) are not
logged, so rev 1's `quiet` categories are dropped — every logged run announces its terminal result
as P87 §6 already does. What remains:

| Risk | Mechanism | Decision |
|---|---|---|
| A one-frame flash of bar on a 20ms op | the bar mounts whenever `activeRun !== null` | **150ms reveal delay** on `.git-dock-progress` (§2.3) — **stands** (user). Row, pill and header still update instantly |

one-row-per-run invariant). The dock still **never auto-expands** (P87 §3.1).
